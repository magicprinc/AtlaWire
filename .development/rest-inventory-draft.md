## 3. Where the mappings and the runtime registry disagree

1. **Registry size and shape.** `manifest.json` holds 192 operations, all `GET`, all
   `kind: json`. The live registry (`atlawire.operations.list_operations()`) holds 202,
   including 3 non-GET semantic reads and 7 binary routes. `bbk-parity.md` also states
   202 entries (199 GET, 3 semantic POST, 7 binary), so the manifest is not a faithful
   projection of the current registry and cannot be substituted for it.
2. **Different registries, not two views of one.** Manifest and runtime registry use
   different operation ids. 10 routes exist only in the runtime registry, 0 only in the
   manifest, and 39 exist in both under a different id.
   Example: `GET /rest/api/1.0/profile/recent/repos` is `bitbucket.profile.recent.repos` in the manifest and `bitbucket.profile.recent-repositories` in the runtime registry.
   A release inventory keyed by manifest id would disagree with the canonical ids in
   `CANONICAL_IDS`/`list_operations()`. The draft keeps the manifest id in
   `mapped_operation_id` and the runtime id in `runtime_operation_id` instead of
   choosing one.
   Runtime routes with no manifest row: `GET /rest/api/1.0/hooks/{hookKey}/avatar`, `GET /rest/api/1.0/projects/{projectKey}/avatar.png`, `GET /rest/api/1.0/projects/{projectKey}/repos/{repositorySlug}/archive`, `GET /rest/api/1.0/projects/{projectKey}/repos/{repositorySlug}/raw`, `POST /rest/api/contentbody/convert/{to}`, `GET /rest/api/2/attachment/{id}/content`, `GET /rest/api/2/attachment/{id}/expand/raw`, `GET /rest/api/2/avatar/{type}/system`, `POST /rest/api/2/search`, `POST /rest/api/2/worklog/list`.
3. **Manifest cannot express metadata.** No manifest operation declares a query field
   (its `arguments` are path parameters only), and every operation reports `kind: json`.
   Query fields and `binary` exist only in `operations.py`, so any release inventory
   built from the manifest alone would silently lose request/response metadata.
4. **Semantic POSTs missing from GET-only denominators.** Bitbucket's denominator is
   GET-only by construction (`D2 standard non-admin GETs`); the mapping has no row for
   `POST /rest/api/1.0/markup/preview`, although the sdk treats it as a read-only POST
   and `%mapping-1` names it as an omission. Jira and Confluence include their semantic
   POSTs in the denominator (2 and 1), so the three products do not share one rule for
   what counts as a read.
5. **Manifest kind vs runtime kind.** 40 rows match a route whose runtime kind is not
   `json`: array=6, object=34. The manifest reports `json` for all of them, so
   response kind must be taken from the registry, not the manifest.
6. **SDK-incompatible paths.** `sdk._validate_path` rejects any path containing an
   `_ADMIN_SEGMENTS` element: `admin`, `application-properties`, `applicationrole`, `audit`, `auditing`, `cluster`, `issuesecurityschemes`, `issuetypescheme`, `license`, `logs`, `mail-server`, `notificationscheme`, `permissions`, `permissionscheme`, `priorityschemes`, `reindex`, `screens`, `settings`, `workflow`, `workflows`, `workflowscheme`.
   9 Bitbucket denominator rows are affected: `application-properties` (n=1, kept
   `required` because the mapping documents it as anonymous) plus 8 `/settings/...`
   routes (n=63, 64, 65, 66, 74, 75, 76, 77). The 5.10 mapping counts all of them as
   non-admin reads, so the registry would refuse routes its own inventory calls
   required. That conflict is the main reason the `/settings/...` rows are `unresolved`.
7. **Rubric disagreement.** Jira/Confluence/Bitbucket mark the same property differently:
   Bitbucket requires full enumeration for `covered`, Confluence accepts a lost response
   envelope, and Jira keeps one documented-but-inconsistent GET (`subtask/move`) inside
   its 109 while also publishing a 108 figure. Only Jira also removes authorization-
   uncertain reads from its denominator (109, or 108 without `subtask/move`; 113 with
   them), while Bitbucket keeps permission-unverified `/settings/...` reads inside its
   66. Mapping `covered/partial/gap` therefore says nothing about whether a `required`
   row is implemented in AtlaWire.
8. **Version labels.** The mappings target `8.22.0` / `6.6` / `5.10.0` while the registry
   documents `Jira Server 8.22.0 REST API 2` / `Confluence Server 6.6.0 REST API` /
   `Bitbucket Server 5.10.0 REST API 1.0`. Confluence 6.6 vs 6.6.0 and the presence of
   `editor2` (not `editor`) in the runtime conversion-target pattern are not reconciled
   by any input here; the `{to}` value set for `contentbody/convert` is unverified.
9. **Path normalization is per-mapping.** Jira rewrites `/rest/session` to
   `/rest/auth/1/session` and prefixes `/rest/api/2`; Confluence rewrites documented
   `/rest/{resource}` to `/rest/api/{resource}` and (for the four audit rows) keeps
   `/rest/audit`; Bitbucket uses `/rest/api/1.0` as written. The draft keeps each
   mapping's written path in `path_as_written` and never re-derives one.

## 5. Row contract

Each `rows[]` entry: `product`, `method`, `reference_version`, `path_normalized`,
`path_as_written`, `source{file,row_group,anchor,index}`, `disposition`, `reason`,
`mapped_operation_id`, `runtime_operation_id`, `duplicate_of`,
`metadata_gaps{manifest_kind,manifest_declares_query_fields,runtime_kind,runtime_query_fields,notes}`.
`row_group` is `denominator` or `excluded_list`. `mapped_operation_id` is null when no
exact route+method exists in `manifest.json`; that is a mapping statement, not a claim
that the route is absent from the runtime registry (see `runtime_operation_id`).
