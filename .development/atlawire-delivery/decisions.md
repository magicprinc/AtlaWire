# Журнал ответственных решений

Зачем файл: по каждому решению, где был выбор, — суть и что выбрано, чтобы через месяц было
видно, почему код такой, и чтобы не «улучшать» его обратно. Правило: если решение можно
отменить без потери гарантии — оно записано как «нет», а не как «есть».

## Принято в 0.9.2

### D-1. Причина ошибки сервера: поле `detail`, а не текст сообщения

**Суть.** Клиент получал `HTTP 400: request failed.` и не знал, что не так. Сервер прислал
причину, но мы её выбрасывали. Соблазн — вклеить причину в `str(error)`.

**Решение.** Причина парсится из документированных полей (`errorMessages`, `errors{}` у Jira;
`errors[]` с `context` у Bitbucket; `message`/`reason` у Confluence) и кладётся в
`AtlaWireError.detail`. `str(error)` остаётся общим: в репозитории есть контрактные тесты,
которые запрещают появление содержимого ответа в сообщении, трейсбеке, stdout и логах, и
ломать этот контракт ради удобства нельзя. CLI печатает `detail` второй строкой — там, где он
нужен человеку.

**Что отброшено.** Дописывать причину в `message`; отдавать тело ответа в тексте; заполнять
`detail` для всех 4xx.

### D-2. `detail` только для HTTP 400

**Суть.** Сначала я включил `{400, 409, 412, 422}` — «на всякий случай».

**Решение.** Оставить только `400`. Это единственный статус, который три продукта реально
вернули на кривые query/JQL/limit в живом прогоне. Для остальных причина не наблюдена, а
угадывать в тексте ошибки хуже, чем молчать: агент начнёт доверять догадке.

### D-3. Причина одна для обоих слоёв

**Суть.** `api-get`/`api-request` идут через слой адаптера (`sdk.py`) и не показывали причину
вовсе, хотя живой Bitbucket-400 её присылает.

**Решение.** Один общий парсер `atlawire.http.error_detail`, вызывается из обоих слоёв; тело
остаётся доступным программно в `SdkRequestError.body`. Иначе агенту пришлось бы помнить, у
какой точки входа ошибки информативнее.

### D-4. `Commit`: вендорские `id` и `displayId`, `hash` — устаревший алиас

**Суть.** Строка коммита отдавала `hash` — имя, которого нет в схеме Bitbucket. В документации
поле называется `id`, а сокращённая форма — `displayId`. Клиент читал `row["id"]` и получал
`KeyError`. Я сначала добавил `id` рядом с `hash` (узаконил дубль), потом ввёл своё имя
`short_id` (второе имя для одного понятия).

**Решение владельца.** Не плодить собственные имена: называть так, как названо у вендора, а
подробности и альтернативы описывать в pydoc. Итог: `id` (полный SHA-1) и `displayId`
(сокращённая форма). `hash` сохранён как устаревший алиас `id`, чтобы код, написанный до
0.9.2, не сломался в момент обновления библиотеки; новый код читает `id`, алиас уйдёт в
следующей мажорной версии. Это одна строка в проекции и одна в TypedDict, а не слой
совместимости, поэтому цена приемлемая.

**Что отброшено.** `short_id` как своё имя; удаление `hash` без переходного периода;
одновременное присутствие трёх имён.

### D-5. Батч-диф: библиотека отдаёт список, CLI — по числу путей

**Суть.** `get_pull_request_diffs` уже был, но CLI принимал один PATH, поэтому клиент делал N
вызовов. Нужно было решить, какую форму отдаёт CLI.

**Решение.** Библиотека: `get_pull_request_diffs` (список объектов) и
`get_pull_request_diffs_text` (один заголовок, файлы по порядку). CLI: без PATH — объект всего
PR, ровно один PATH — объект файла, два и больше — список. Причина: `--source-path` (нужен для
переименованного файла) осмыслен только для одного файла, и ломать существующую форму
«один файл = один объект» ради единообразия значит ломать вызывающих без выигрыша.

**Что отброшено.** Всегда возвращать список при любом PATH; отдельная команда `pr-diffs`.

### D-6. Заголовок диффа говорит правду

**Суть.** В заголовке было жёстко `whitespace=ignore-all`, даже когда вызывающий передал
`ignore-none`. Это ложь в артефакте ревью.

**Решение.** Печатать фактический режим и факт обрезки (`declared-truncation=none`). Именно
«объявленной»: незаявленный серверный cap не детектируется, и обещать обратное нельзя.

## Ревью своих решений: что я перемудрил и убрал

### R-1. `verify()` проверял документ сам против себя — убрано

**Суть.** Артефакт генерируется, а `--check` сравнивает байты с свежей сборкой. Значит любая
ручная правка файла уже ловится. Я же добавил ~90 строк, которые сверяли `counts.rows`,
`counts.excluded_by_reason`, `registered`, `runtime_operation_id`, `response_kind` с содержимым
того же документа. Такие проверки могут сработать только на словаре, собранном тестом, — то
есть существовали ради собственных тестов.

**Решение.** Оставить три вопроса: совпадают ли замороженные числа, разрешается ли каждая
required-строка в операцию реестра (и наоборот), тот ли набор исключений (по хэшу). 180 строк
→ 85; шесть тестов, проверявших снятые проверки, удалены.

**Правило на будущее.** Проверка, которая не может сработать на реальном входе, — это не
защита, а стоимость.

### R-2. Обратная сверка прозы маппинга — убрано

**Суть.** Я сверял константу audit-путей с прозой `exclusion_rule` в обе стороны. Прямая
сверка полезна: она не даёт константе разойтись с доказательством. Обратная ловила бы
ситуацию «в прозе назван маршрут, которого нет в константе» — то есть правку документа,
которую и так видно в диффе.

**Решение.** Оставить только прямую проверку.

### R-3. Тест версии не должен поднимать подпроцесс и allowlist окружения

**Суть.** Для C8 я написал ~100 строк: подпроцесс, список разрешённых переменных, проверка
пути. Задача — сравнить два значения.

**Решение.** 20 строк: `importlib.metadata.version("atlawire")` против
`atlawire.__version__`, с `skip` если пакет не установлен. Тест сразу поймал реальное
расхождение 0.9.1/0.9.2 при сборке — работает.

### R-4. Дубль `id` рядом с `hash` — убран (см. D-4)

Совместимость ради совместимости: агенты не «привыкли» к нашему `hash`, он был просто
неудачным именем. Лучше сломать один раз и назвать правильно.

## Принято в 0.9.4: поверхность API с самих серверов

### D-7. Источник API — WADL нашего сервера, а не сайт документации

**Суть.** Задача была скачать официальную документацию Jira 8.22 и Confluence 6.6.
Проверка показала, что сайт этих версий больше не отдаёт: `/rest/v660/` отвечает 302 на
`22.x`, у Jira опубликованы только 10.x. Скачанный HTML описывал бы релиз, которого у нас нет.

**Решение.** Читать `application.wadl` с каждого нашего сервера: он генерируется из
работающего кода, поэтому описывает именно наш инстанс. Версии подтвердились ровно: Jira
8.22.2, Bitbucket 5.10.0. Confluence версию по REST не отдаёт → `null` и sha256 артефакта, а
не выдуманная цифра.

**Что отброшено.** Скачивание HTML и конвертация в Markdown (описывает не наш релиз);
догадки о версии Confluence по маппингу.

### D-8. Нарезка: группа = литеральный сегмент маршрута

**Суть.** Первая версия дала файл на 66 КБ (все `projects` Bitbucket). Такой файл нельзя
читать «по одной теме» — он грузится целиком, и смысл базы теряется.

**Решение.** Группа — первый литеральный сегмент после группы; placeholder (`{projectKey}`)
группой не считается, это родительская ссылка. Крупные группы режутся автоматически, порог 40
методов. Итог: 103 файла, крупнейший 57 КБ, Jira вся ≤ 12 КБ.

**Что отброшено.** Резать по числу строк (рвёт методы); отдельный файл на каждый метод
(сотни файлов, нечем пользоваться).

### D-9. Сверка реестра с сервером — обязательная, с замороженным эталоном

**Суть.** Ради чего всё делалось: проверить, что мы реализовали то, что сервер реально
обслуживает.

**Решение.** `tools/check_api_surface.py` считает три разницы: маршруты сервера, которых у
нас нет; наши маршруты, которых сервер не обслуживает; совпавшие маршруты с query-полями,
которые сервер документирует, а мы не объявляем. Эталон заморожен: числа **и** sha256 обоих
списков **и** sha256 самого WADL. Числа без идентичности зеленели бы при переименовании на
обеих сторонах.

**Итог сверки:** совпало 58 Bitbucket, 35 Confluence, 105 Jira. Расхождения — админские
маршруты, исключённые осознанно, каждый с причиной в `not_in_wadl`; у Jira два
недокументированных WADL маршрута (`attachment/{id}/content`, `rest/auth/1/session`), тоже с
причиной.

**Что отброшено.** Сравнивать только количества (пропускает переименования); считать
расхождения ошибкой сборки (админские маршруты исключены намеренно).

### D-10. Внутренний хост вычищается из артефактов

**Суть.** WADL содержит `base="https://<наш хост>/rest/..."`. Артефакты попадут в публичный
репозиторий.

**Решение.** Заменяются все написания: хост, authority с портом, верхний регистр; после
замены проверяется, что ни одного не осталось, и при остатке запись отменяется. Тест
проверяет, что в артефактах есть только `example.com`.

**Закрыто по решению владельца 2026-11-25.** Хосты вычищены из текущих файлов (история не
переписана). Заодно удалены страницы, не относящиеся к Atlassian: описание публичного API
другого продукта (`.development/api/`) и строка про копию прода несвязанной БД. Упоминания
посторонних инструментов (брокеры сообщений, поисковый индекс, граф кода) в документах
обезличены: смысл предложений сохранён, имена убраны.

### D-11. `get_issue(expand=None)`

**Суть.** Сверка показала, что мы всегда отправляем `expand`, поэтому серверный дефолт
недостижим через типизированный вызов — при том что `expand` документирован как обычный
query-параметр.

**Решение.** `expand: str | None`, дефолт остался `"renderedFields"` (наш выбор, теперь это
написано в pydoc), `None` опускает параметр.

**Что отброшено.** Сделать дефолтом `None` (изменило бы выдачу существующих вызовов).

### R-5. Сверка резала trailing-placeholder — оказалось дефектом

**Суть.** Чтобы сравнить наш `/diff` с серверным `diff{path}`, нормализация отбрасывала
хвостовой `{}`. Это сделало `/attachment/{id}` равным `/attachment` и **склеило 15
зарегистрированных GET-маршрутов Bitbucket** с соседними. Первые опубликованные числа
(42/25/81) были занижены.

**Решение.** Вместо отбрасывания — разворачивать в набор вариантов: glued-суффикс
(`diff{path}`) даёт `/diff` и `/diff/{}`, хвостовой `/{id}` остаётся собой. Правило применено
к обеим сторонам. Числа после исправления: 58/35/105 совпавших.

**Правило.** Нормализация, которая «упрощает» сравнение, должна доказывать, что не склеивает
разное; иначе она прячет дефекты вместо поиска.

### D-12. Query-параметры берутся из WADL, ручное объявление главнее

**Суть.** `read <id>` отвергает любое query-имя, которого нет в реестре. Сервер при этом
документирует 284 параметра на 96 маршрутах, и они были недостижимы через типизированный
вызов — это и был `params_14`.

**Решение.** `tools/build_query_surface.py` превращает WADL в `src/atlawire/query_params.json`,
реестр сливает его при импорте. Ручное объявление всегда главнее: оно несёт ограничения,
которых в WADL нет (enum, форма пути, «ровно один из»), и сгенерированная строка не имеет
права ослабить проверку. Поле получило `source`: `atlawire` или `server-wadl`.

**Итог:** 113 операций с объявленными параметрами (358 полей) вместо 22; сверка с сервером
даёт **0** маршрутов, где сервер документирует параметр, а мы нет.

**Найденный дефект.** Первая версия генератора читала реестр, который сам же наполняет:
второй прогон принимал свой вывод за ручное объявление и давал меньше строк — файл не был
неподвижной точкой. Лечится пометкой `generated` у сгенерированных полей.

### D-13. Готовой библиотеки WADL не берём

**Суть.** Поиск по PyPI и сети: `wadllib` 2.1.0 (Canonical) — единственный живой вариант, но
LGPL-3.0, тянет `lazr.uri`, и API заточен на навигацию и запросы, а не на извлечение трёх
полей (маршрут, имя, тип). `pyware` на PyPI — чужой пакет с тем же именем; `wadl2swagger` без
лицензии; `wadler` по описанию автора — POC.

**Решение владельца:** `lib_a` — не ставить зависимость, а убрать дубль. Общий разбор WADL
вынесен в `tools/wadl_surface.py`; XML разбирает уже установленный `defusedxml`.

**Что отброшено.** `wadllib` ради трёх полей; `wadl2swagger` ради лишнего слоя конвертации.

### D-14. Административные чтения объявлены, но за явным опт-ином

**Суть.** Вопрос владельца: admin-API что-то опасное возвращает? Проверка живьём показала, что
под нашим токеном часть отвечает 200 (`/admin/groups`, `/admin/users`,
`/application-properties`, Jira `/worklog/deleted|updated`), часть — 401/403. Опасного они не
отдают: это списки групп/пользователей и свойства приложения. Но это уже не «non-admin», и
скрывать их значило гонять потребителя в `api-get` без валидации, пагинации и operation id.

**Решение владельца:** вариант `admin_b` — объявить, но за флагом.

**Как сделано.** 117 операций получили `scope="admin"`; `read` отказывает им без
`allow_admin=True` **до** любого запроса. Замка два независимых: гейт реестра и валидатор пути
в транспорте, поэтому ошибка в одном ловится другим. Сообщение транспорта осталось прежним
(`api-get` флага не имеет, подсказка про `--allow-admin` была бы там ложью); подсказка живёт в
сообщении реестра.

**Границы.** Три маршрута не объявлены никогда: Jira `GET /issue/{key}/subtask/move` (GET,
меняющий состояние) и два бинарных тела (Jira `/email-templates`, Confluence `/audit/export`).
Они лежат в `admin_operations.json` → `deferred` с причиной, чтобы исключение было проверяемым.

**Гарантия «только чтение».** `tools/check_read_only.py` проверяет все 319 операций двумя
способами: метод (GET плюс три аудированных семантических POST) и первое слово документации
(«Returns» — чтение, «Delete»/«Move»/«Create» — нет). Гейт в CI.

**Итог сверки с серверами:** Bitbucket 100/100 объявленных GET, Confluence 44/45, Jira 171/173;
остаток — ровно отложенные три маршрута.

### R-6. Генератор, читающий свой же вывод — второй раз

**Суть.** Генератор admin-операций собирал «уже зарегистрированные» маршруты из реестра,
который сам же и наполняет. Первый прогон дал 117, второй — **0**: свой вывод он принял за
существующие маршруты. То же самое раньше случилось с query-генератором.

**Решение.** Оба генератора игнорируют `scope="admin"` при сборе «уже объявленного», а
`tests/test_spec_generated_surfaces.py` требует, чтобы второй прогон совпадал с первым и чтобы
admin-файл никогда не становился пустым.

**Правило.** У любого генератора, читающего реестр, который он наполняет, обязан быть тест
«второй прогон = первый».

### D-15. Параметр с документированным побочным эффектом не отправляется никогда

**Суть.** Ревью показало, что гарантия «только чтение» проверялась по методу и тексту
описания, но не по параметрам. Jira документирует `updateHistory` у `GET /issue/{key}` как
добавление задачи в историю просмотров текущего пользователя — то есть изменение, а не чтение.
Параметр был объявлен в сгенерированной query-поверхности (283 поля) и доступен через `read`,
`api-get` и публичный `request_json`; в типизированном `get_issue` был отдельный флаг.

**Решение.** Один короткий список в `http.py` (`SIDE_EFFECT_QUERY`) — источник истины для всех
слоёв. Его проверяют: реестр (`_validated_query`), слой адаптера (`_checked_params`, через
который идут `api-get`/`api-request` и `request_json`) и генератор query-поверхности. Флаг
`--update-history` и аргумент `update_history` удалены совсем: читалка не должна предлагать
действие, которое меняет состояние пользователя.

**Что отброшено.** Оставить как opt-in (это всё равно «добавление»); полагаться только на
allowlist сгенерированных имён (тогда `api-get` остаётся обходным путём).

**Как это удержано.** `check_read_only.py` считает появление такого параметра ошибкой, а
`tests/test_spec_side_effect_parameters.py` проверяет отказ во всех трёх точках входа, включая
регистр и «безопасный» параметр рядом.

### D-16. Отчёт аудита не молчит о том, чего не может прочитать

**Суть.** 40 read- и 16 admin-операций не имеют текста в WADL. Для них проверка «первое слово
описания» ничего не читала и проходила молча — именно так мог бы проскочить `subtask/move`.

**Решение.** Для маршрута без документации включается независимый признак: сегменты пути из
короткого списка изменяющих глаголов (`move`, `transition`, `delete`, …). Документированные
маршруты по-прежнему судятся по тексту, потому что многие чтения законно содержат такое слово.

**Что отброшено.** Требовать документацию у всех (56 маршрутов её не имеют — гейт стал бы
красным без пользы); доверять только списку исключений (он не ловит новое).

### R-7. Проверка отчёта ревью: два замечания отброшены как ложные

**Суть.** Повторная проверка отчёта по коду показала:

- `describe_33` — недостижимо: `_product_of_operation` отсекает неизвестный ID до
  `describe_operation`, оба читают один реестр. Теста-доказательства трассировки нет, поэтому
  и исправления нет.
- `dupe_scanners_43` и `dupe_pagers_46` — сужены: одинаковое имя `_scan_repository` описывает
  разные задачи (поиск содержимого и инвентарь расширений), общий пагинатор для трёх продуктов
  не обоснован различием правил остановки. Реальным оказался дрейф трёх копий `_split_repo`;
  он закрыт тестом на совпадение вердиктов, без слияния модулей.

**Остальные подтверждены и исправлены:** конверт ошибок у `api-get`/`api-request`, потеря
категории на локальном сбое записи, `--check` у двух генераторов, потерянный `totalSize` в
типизированном space-content, `max_pages` без проверки типа, `.strip()` до проверки типа.

**Правило.** Отчёт ревью — гипотезы. Каждый пункт либо подтверждается ссылкой на код и
тестом, либо отклоняется с причиной.

## Не делал, хотя предлагалось

- **Валидация JQL до запроса.** Клиент просил «объяснить причину»; сервер уже объясняет, а
  свой парсер JQL — это второй источник правды, который разойдётся с сервером.
- **Кэш `titles` как у BBK.** Кэш — это устаревшие ответы; батчи по 50 закрывают стоимость.
- **Свои `list_comments`/`list_versions`.** Функции уже есть под вендорскими именами
  (`get_page_comments`, `get_page_history`, `list_issue_comments`); проблема была в
  документации, а не в API.
- **Батч-диф как отдельная команда.** Расширение существующей формы дешевле для вызывающего.
