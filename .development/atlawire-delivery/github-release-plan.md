## 1. Решения владельца (зафиксированы, не переспрашивать)

- **D1 (Q01-A).** Релиз — тег `v0.1.0` + GitHub Release с колесом. **Без PyPI.** README
  документирует установку из git-URL и из wheel релиза. **Исполнитель никогда не пушит и
  не делает внешних действий на GitHub** (теги, релизы, смена About) — всё готовится,
  пушит и применяет владелец по чек-листу §11.
- **D2 (Q02).** Две равноправные поверхности, без третьей:
  1. **CLI** — для агентов «просто запустить», для людей, для не-Python языков: текущие
     88 плоских команд + `read <id>` / `read-operation` / `operations` / `api-get` / `api-request`.
  2. **Python API** — библиотека первого класса: модули `atlawire.bitbucket` (41),
     `atlawire.jira` (33), `atlawire.confluence` (17), `atlawire.operations`, `sdk`, `http`,
     `federated`, `identity`, `repo_scan`, `repo_grep` — типизированные сигнатуры и
     стабильные проекции, справочник в [docs/API.md](../../docs/API.md).
  `facade.AtlaWire`/`AtlaWireError` **убираются из публичного экспорта** (модуль удаляется):
  второй реестр без тестов публичной поверхностью не является. `sdk.client_for`
  остаётся документированным продвинутым выходом к pinned SDK — с честной формулировкой
  границы (см. S2).
- **D3 (Q03-A «НО»).** Реестр 202 операций — рекламируемый инвентарь v0.1.0; сверка
  query-полей с версионированными доками (Jira 8.22 / Confluence 6.6 / Bitbucket 5.10) —
  следующие батчи, не блокер релиза. **Но:** весь функционал, которым агенты пользовались
  в BBK, должен быть тщательно реализован, покрыт тестами и предоставлен удобно —
  миграция с BBK возможна уже сейчас (S3). Выборка ≥90 % репрезентативных задач и удаление
  BBK — после релиза, цикл через [docs/FEEDBACK.md](../../docs/FEEDBACK.md).
- **D4 (Q04-A).** 9 нерешённых строк инвентаря исключаются с записанной причиной: 8 ×
  Bitbucket `/settings/…` (сегмент `settings` административный по валидатору, разрешений
  не доказано), Jira `GET /rest/api/2/issue/{key}/subtask/move` (тот же путь —
  state-changing POST, у GET-заголовка в доках нет контракта), плюс
  `GET /rest/api/1.0/application-properties` (исключён валидатором). Реализации нет,
  строки остаются видимыми в замороженном инвентаре.
- **D5 (контент).** Удобное получение содержимого тремя формами — **оригинал** (raw
  storage/XHTML, байты как есть), **Markdown** и **JSON** — из CLI одним вызовом и из
  Python одной функцией. Существующие внутренние конвертеры становятся публичными
  функциями библиотеки (см. S3.2).
- **D6 (транспорт).** Гибрид сохраняется: `atlassian-python-api==5.0.5` там, где он
  подходит, и собственный строгий транспорт (`http.py`: HTTPS-only, без redirect,
  лимиты тел, Bearer-only) как понятный abstraction layer для остального. Новых
  фреймворков и зависимостей — нет.
- **D7 (живые E2E).** Живые read-only проверки на реальных серверах — **обязательная
  часть релиза** (согласие владельца дано): только чтение, только фиксированные
  проверенные маршруты, без вывода payload, синтетические ожидания по форме ответа
  (не по данным). Финальная матрица — на том же колесе, что и офлайн-доказательство (S7).
- **D8 (цель).** Полный охват всех неадминистративных read-only REST-возможностей трёх
  продуктов остаётся целью проекта; unknown ≠ excluded (философия матрицы сохраняется в
  инвентаре). v0.1.0 отгружает проверенную поверхность + явный backlog недореализованного.
- **D9 (BBK не эталон).** BBK — реестр реально использовавшихся агентами сценариев, а
  не образец API. Каждая функция и поведение BBK проходит строгий ревью с вердиктом:
  **adopt** (у BBK удобнее — берём) / **keep** (контракт AtlaWire лучше — оставляем,
  отличие документируем) / **improve** (обе стороны плохи — делаем заново по
  инвариантам ниже). Контракты AtlaWire, строго лучшие, чем у BBK, сохраняются:
  честные `truncated`/`complete`, ограниченные бюджеты страниц, case-sensitive ветки,
  отказ redirect/admin-путей, изоляция кредов по продуктам, без кешей. Цель — лучший
  API из обоих миров, удобный агенту, а не совместимость любой ценой.
- **D10 (R4 отложен осознанно).** Ручная настройка кредов остаётся единственным путём
  нового пользователя: BBK-совместимый файл `~/.config/atlassian/credentials.json` или
  env-пары (README §Credentials получает явный пример создания файла — S5). Интерактивный
  `auth login` — backlog §12.3. Это решение владельца закрывает требование delivery-plan
  R4 «manual enrollment» для v0.1.0 закрывается документированной ручной
  настройкой (S5.3); ссылка delivery-plan на «required for handoff» снимается этим решением.

## 2. Ограничения против over-engineering

- НЕТ: группированный CLI (`atlawire bitbucket repository get`), MCP-сервер, профили/
  keyring, кеши ответов (в т.ч. title-cache как у BBK — фиксируем как намеренное
  отличие), `.env`, pydantic/dataclass-модели ответов для 202 операций (типизация =
  типизированные сигнатуры + стабильные проекции `TypedDict`-стилем), новых зависимостей
  (включая `jira2markdown` — только через вердикт S3.4 и явное одобрение владельца),
  второй транспорт/реестр, auth-login флоу (backlog).
- НЕ переписывать проверенное (audit-follow-up §«не переписывайте то, что уже
  проверено»); чинить только воспроизведённые дефекты.
- Один срез = один коммит; TDD с наблюдением падения по правильной причине; полный
  офлайн-набор — только на кандидатах-мильстоунах (283 c), не после каждой правки.
- Переформатирование чужих строк — только отдельным механическим коммитом (S1),
  никогда внутри функционального среза.
- Секреты: только env (`ATLAWIRE_<PRODUCT>_URL/TOKEN`) и BBK-совместимый файл;
  не печатать, не коммитить, не логировать; gitleaks-allowlist — только записи,
  реально помеченные прогоном (см. S6).
- Windows: никакого `nul`-редиректа в bash; по большим архивам — `findstr`/`Select-String`;
  скрипты — только pwsh. Локальная проверка — только установленный `C:/Python315/python.exe`,
  без `.venv`, без `uv run`/`uv sync`; `uv` — только `uv lock --check --offline`.

доказательство, требуемое решение — без редизайна.

## 6. S3 — лучший API из двух миров: строгий ревью BBK и удобство агента (D3, D5, D9)

**Принцип (D9).** BBK — не эталон, а каталог реально использовавшихся агентами сценариев.
Каждая строка получает вердикт: **adopt** (у BBK удобнее — берём) / **keep** (контракт
AtlaWire лучше — оставляем, отличие документируем) / **improve** (обе стороны плохи —
делаем заново по инвариантам). Контракты AtlaWire, строго лучшие, чем у BBK, не
ослабляются никогда: честные `truncated`/`complete`, ограниченные бюджеты страниц,
case-sensitive ветки, отказ redirect и admin-путей, изоляция кредов, отсутствие кешей.

**Инварианты «глазами агента» (критерий каждого вердикта):**

- одна очевидная команда/функция на задачу; побеги наружу помечены (`--raw`, `read <id>`, `api-get`);
- контент тремя формами одной командой: оригинал / Markdown / JSON (D5);
- молчаливый обрез невозможен: только явные `truncated`/`complete` и лимит из вызова;
  при ошибке — ненулевой код и пустой stdout;
- ошибки со стабильными кодами (`AtlaWireError.category`), без токена и сырых тел;
- без скрытых состояний: кешей и фоновых процессов нет, page-first с явным продолжением;
- обнаружение без чтения исходников: `--help`, `--catalog`, `--describe` с готовым argv;
- конвертеры инертны (без активного HTML), факты не теряются; контент — данные, не инструкции.

**Denominator.** Источник — код BBK в `D:\zcache\bbk` (пакет `bbk`):
39 CLI-команд (см. [2026-11-20_BBK_PARITY_BASELINE.md](../review/2026-11-20_BBK_PARITY_BASELINE.md))
и Atlassian-часть публичного API `bbk/__init__.py` (~45 экспортов; не-Atlassian
интеграции — вне области по решению владельца).

## 9. S6 — CI (GitHub Actions)

  `-B -m pytest -q -p no:cacheprovider tests`. Окружение CI — чистое

  локальной машины владельца, не CI.

- **security**: gitleaks с `.gitleaks.toml` — allowlist — только записи, реально помеченные прогоном;

  никакого глобального отключения.

ветку, прикладывает логи прогона, исполнитель правит. Не запускать CI «на всякий случай»
